# Архитектура

Документ отвечает на два вопроса: как система устроена и **почему именно так**.
Второе важнее — устройство видно из кода, причины нет.

---

## 1. Главное ограничение

Это система тайного голосования. Из этого следует всё остальное.

| Инвариант | Почему он важнее производительности |
|---|---|
| Нет связи «студент → кандидат» | Существование такой связи где угодно — в схеме, логах, метриках — делает голосование не тайным |
| Один `VoteRecord` + один `Ballot` в одной транзакции | Частично записанный голос нельзя ни засчитать, ни отменить |
| Один голос гарантирует ограничение базы | Проверка на Python между чтением и записью не выдерживает параллельных запросов |
| Голос пишется синхронно | Очередь означает «мы ответили успехом, а записали потом, может быть» |
| Redis — ускоритель, не источник истины | Полная потеря Redis не должна менять ни одного зафиксированного голоса |

Приоритет при любом конфликте (ТЗ п.118):

```
КОРРЕКТНОСТЬ → ЦЕЛОСТНОСТЬ ГОЛОСА → ТАЙНА → БЕЗОПАСНОСТЬ → ПРОИЗВОДИТЕЛЬНОСТЬ → ЭКСПЛУАТИРУЕМОСТЬ
```

## 2. Топология

```
                     ┌──────────────┐
   клиенты  ────────▶│ LB / Nginx   │  TLS, статика, медиа, rate limit
                     └──────┬───────┘
                            │  без sticky sessions
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
    ┌───────────┐     ┌───────────┐     ┌───────────┐
    │ Django #1 │     │ Django #2 │     │ Django #N │   gunicorn, gthread
    └─────┬─────┘     └─────┬─────┘     └─────┬─────┘
          └────────┬────────┴────────┬────────┘
                   ▼                 ▼
            ┌─────────────┐   ┌─────────────┐
            │  PgBouncer  │   │    Redis    │  кэш личности, статус голоса,
            └──────┬──────┘   └─────────────┘  результаты, троттлинг, брокер
                   ▼
        ┌──────────────────────┐
        │ PostgreSQL primary   │◀── ВСЕ записи и все критичные чтения
        └──────────┬───────────┘
                   │ streaming replication
                   ▼
        ┌──────────────────────┐
        │ PostgreSQL standby   │◀── только новости, FAQ, страницы, вузы
        └──────────────────────┘

    ┌──────────────┐        ┌────────────────────┐
    │ Celery       │        │ Объектное хранилище│  медиа
    │ импорт/экспорт        └────────────────────┘
    │ уведомления  │        НИКОГДА не голоса
    └──────────────┘
```

**Никаких sticky sessions.** Состояния в процессе приложения нет:
аутентификация — по JWT, кэш — общий Redis, медиа — объектное хранилище.
Падение одной ноды не затрагивает пользователей остальных; проверки
конфигурации не дают развернуть схему, где это не так.

## 3. Слои и границы

```
views          тонкие: разбор запроса, вызов сервиса, формирование ответа
  │
services       вся бизнес-логика и правила голосования
  │
db_locks       сериализация конкурентного доступа (advisory locks)
cache*         политика кэширования: что, насколько и почему
  │
models         схема и ограничения базы
```

| Модуль | Ответственность | Почему отдельно |
|---|---|---|
| `apps/voting/services.py` | приём голоса, статус голосования | Единственное место, где принимается голос. Правила не должны существовать в двух копиях |
| `apps/elections/services.py` | смена состояния выборов | Переход состояния конфликтует с голосованием и обязан быть сериализован |
| `apps/elections/aggregates.py` | результаты и явка одним запросом | Подсчёт в цикле по кандидатам не масштабируется |
| `apps/core/db_locks.py` | advisory-локи | Ключ лока обязан быть стабильным между процессами; ошибиться легко, а цена — молча сломанный барьер |
| `apps/core/cache*.py` | ключи, TTL, инвалидация, безопасные обёртки | Политика кэширования нетривиальна и должна быть в одном месте |
| `apps/core/db_replica.py` | что можно читать с реплики | Ошибка здесь показывает студенту устаревший статус голоса |
| `apps/core/system_checks.py` | проверки перед деплоем | Небезопасная конфигурация не должна запускаться молча |

Границы защищены структурными тестами: `tests/contract/test_code_structure.py`
не даёт логике блокировок и кэша вытечь во view,
`tests/contract/test_read_replica.py` — пометке реплики попасть в голосование.
Такие нарушения не ломают ни один тест поведения, поэтому проверяются иначе.

## 4. Путь голоса

```
POST /api/v1/vote/
  │
  ├─ JWT: подпись → is_active → auth_version
  │    личность из Redis; при попадании — 0 запросов к базе
  │    при промахе — один SELECT и запись в кэш
  │
  ├─ троттлинг по студенту, а не по IP
  │    кампус за одним NAT иначе заблокировал бы сам себя
  │
  └─ cast_secret_ballot()  ← единственная точка приёма голоса
       │
       BEGIN
       ├─ pg_advisory_xact_lock_shared(выборы)
       │     SHARED: голоса не ждут друг друга, ждёт только смена состояния
       ├─ SELECT выборы          статус, окно, университет
       ├─ SELECT кандидат        принадлежит ли этим выборам
       ├─ SAVEPOINT              без него IntegrityError ломает транзакцию
       ├─ INSERT VoteRecord      ← UNIQUE(выборы, студент) решает исход гонки
       ├─ RELEASE SAVEPOINT
       ├─ INSERT Ballot          ← ни студента, ни JWT, ни IP
       COMMIT
       │
       └─ после COMMIT: кэш статуса, лог, метрика
            в логе нет пары студент+кандидат, в метрике нет кандидата
```

**Университет берётся только из аутентифицированной личности**, никогда из
тела запроса.

**Двойной голос отвергает база**, а не Python. При двух одновременных
запросах одного студента второй `INSERT` нарушает UNIQUE и превращается
в `already_voted`. `Ballot` при этом не создаётся: дубликат не должен
добавлять бюллетень.

**Успешный HTTP-ответ — только после реального COMMIT.**

## 5. Как устроена тайна голосования

```
VoteRecord:  (выборы, студент, время)     ← кто участвовал
Ballot:      (выборы, кандидат, время)    ← за кого подан голос
```

Связи между ними нет и быть не может. Запрещённые связи:
`Student → Candidate`, `Student → Ballot`, `VoteRecord → Candidate`,
`VoteRecord → Ballot`.

Восстановить выбор человека можно не только через схему, поэтому закрыты
и остальные пути:

| Путь утечки | Чем закрыт |
|---|---|
| Логи | фильтр не пропускает `student_id` и `candidate_id` вместе; тело `POST /vote` и заголовок `Authorization` вырезаются |
| Метрики | у счётчиков голосования есть метка выборов и исхода, метки кандидата нет |
| Время | `Ballot.cast_at` не связан ни с чем, что идентифицирует человека |
| Порядок строк | оба идентификатора — UUID, а не последовательные числа |

## 6. Роль Redis

**Redis никогда не является источником истины о голосе.** Полная очистка
Redis не меняет ни одного зафиксированного голоса — это проверяется тестом.

| Что хранится | Зачем | Что будет без Redis |
|---|---|---|
| Личность студента | убрать SELECT на каждый запрос | SELECT на каждый запрос |
| Факт участия | быстрый ответ «вы уже голосовали» | чтение из PostgreSQL |
| Результаты и явка | тяжёлые агрегаты | пересчёт при каждом запросе |
| Счётчики троттлинга | ограничение частоты | ограничение не работает |

Кэшируется **только положительный** факт участия: он необратим. Отрицательный
не кэшируется вовсе — устаревшее «вы ещё не голосовали» показало бы кнопку
голосования повторно.

Все обращения к кэшу идут через обёртки, которые ловят любое исключение:
недоступный Redis обязан замедлить систему, а не уронить.

## 7. Что уходит в Celery и что не уходит никогда

| В очередь | Никогда в очередь |
|---|---|
| импорт студентов | **приём голоса** |
| выгрузка результатов | подсчёт результатов при выдаче |
| уведомления | смена состояния выборов |
| обслуживание | |

Голос, ушедший в очередь, означает ответ «успех» до того, как что-то
записано. Для голосования это недопустимо.

## 8. Чтения с реплики

Реплика включается переменной `DB_REPLICA_HOST`. Пока её нет, всё читает
primary — безопасное состояние по умолчанию.

Чтения **не** роутятся автоматически. Роутер Django выбирает базу по модели,
а нужный критерий — смысл запроса: `VoteRecord` читается и в проверке
«голосовал ли я» (отставание недопустимо), и в отчёте по явке (отставание
безвредно). Роутер их не различит.

Поэтому реплика подключается явной пометкой `eventual()`:

| Читает primary | Может читать реплику |
|---|---|
| приём голоса и всё, что он проверяет | новости |
| статус голосования | FAQ |
| смена состояния выборов | статические страницы |
| результаты | справочник вузов |
| аутентификация | |

Направление ошибки выбрано намеренно: забытая пометка стоит лишней нагрузки
на primary, забытый запрет — показывает студенту, что он не голосовал,
после того как он проголосовал.

## 9. Где узкое место сейчас

После второй итерации оптимизации (этап 11) — **CPU приложения**.
PostgreSQL при втрое большей нагрузке тратит меньше процессора, чем раньше:
он перестал порождать backend-процесс на каждый HTTP-запрос.

Измерения и то, чего они не доказывают, — в
[docs/PROFILING.md](PROFILING.md) и [docs/PERFORMANCE.md](PERFORMANCE.md).

## 10. Что архитектура допускает, но что не сделано

- **Шардирование по вузу или выборам.** Не введено намеренно: преждевременное
  шардирование усложняет всё и ничего не ускоряет, пока нет доказательств
  необходимости. Границы данных при этом уже проходят по вузу, так что
  будущее разделение возможно.
- **Отдельный сервис голосования.** Не выделен: доказательств необходимости
  нет, а вынос единственной транзакционно-критичной операции за границу
  процесса добавил бы отказов ровно там, где их допускать нельзя.
