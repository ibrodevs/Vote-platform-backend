# Профилирование и вторая итерация оптимизации (этап 11)

**Дата:** 2026-09-23
**Пункты ТЗ:** 83, 84, 117, 119, 120, 127

Этап 11 запрещает оптимизировать что-либо, не показанное измерением (ТЗ п.83,
84). Поэтому документ построен так: сначала чем и что измерено, потом сырые
числа, потом решения — включая решения **не** делать.

---

## 1. Окружение

| Параметр | Значение |
|---|---|
| CPU | 8 ядер, общих для приложения, PostgreSQL, Redis и генератора нагрузки |
| Docker RAM | 3.8 GiB на все контейнеры вместе |
| Сеть | loopback, задержки между приложением и базой практически нет |
| Django / Python | 5.2.17 / 3.11.16 |
| PostgreSQL | 16.15, `max_connections=300` |
| Сервер приложения | gunicorn, 4 воркера × 4 потока, gthread |
| Профиль нагрузки | D — запись голосов (ТЗ п.82) |
| Троттлинг | выключен: измеряется приложение, а не ограничитель (ТЗ п.36) |

**Что это окружение позволяет узнать и что нет** — раздел 7.

---

## 2. Инструменты

| Срез | Чем снят | На какой вопрос отвечает |
|---|---|---|
| Распределение CPU | `docker stats` в пике | Кто из компонентов ест ядра |
| Время базы по запросам | `pg_stat_statements` + `manage.py pg_hot_statements` | Какие запросы дороги **на самом деле** |
| Ожидания в базе | `pg_stat_activity.wait_event` | Ждут ли голоса блокировок |
| CPU приложения | py-spy по воркеру gunicorn | Где горит Python |
| Обращения к базе | `tests/performance/test_query_budget_vote.py` | Сколько round trips стоит голос |

`pg_stat_statements` отдаёт нормализованные запросы — литералы заменены на `$1`.
Ни email, ни `student_id`, ни `candidate_id` в выводе появиться не могут:
тайна голосования (ТЗ п.3, 4) обеспечена самим источником данных, а не
аккуратностью того, кто читает отчёт.

## 3. Что показали измерения

### 3.1. Бюджет обращений к базе: 9 round trips на голос

Зафиксировано тестом `tests/performance/test_query_budget_vote.py`:

| # | Обращение | Зачем |
|---|---|---|
| 1 | `BEGIN` | транзакция |
| 2 | `SELECT pg_advisory_xact_lock_shared(...)` | SHARED-лок выборов (ТЗ п.8) |
| 3 | `SELECT ... FROM elections WHERE id = ...` | статус, окно голосования, университет |
| 4 | `SELECT 1 FROM candidates ... LIMIT 1` | кандидат принадлежит этим выборам |
| 5 | `SAVEPOINT` | без него `IntegrityError` ломает транзакцию (ТЗ п.10) |
| 6 | `INSERT INTO voting_voterecord` | факт участия |
| 7 | `RELEASE SAVEPOINT` | |
| 8 | `INSERT INTO voting_ballot` | бюллетень |
| 9 | `COMMIT` | |

Отказ дубликату стоит столько же.

Это единственная метрика этапа, **не зависящая от железа**: на ноутбуке
loopback делает эти обращения почти бесплатными, на боевом сервере между
приложением и базой появляется сеть.

### 3.2. Скрытые запросы, которых приложение не делает

`pg_stat_statements` показал то, чего нет в коде — проверки внешних ключей,
которые PostgreSQL выполняет сам:

```
10865  SELECT 1 FROM ONLY students_student   x WHERE id = $1 FOR KEY SHARE OF x
21730  SELECT 1 FROM ONLY elections_election x WHERE id = $1 FOR KEY SHARE OF x
10865  SELECT 1 FROM ONLY candidates_candidate x WHERE id = $1 FOR KEY SHARE OF x
```

На каждый голос — **четыре** дополнительных внутренних запроса (выборы
проверяются дважды: для `VoteRecord` и для `Ballot`). Они дёшевы и являются
платой за ссылочную целостность, которую убирать нельзя. Зафиксированы, чтобы
не искать потом «откуда лишняя нагрузка».

### 3.3. Профиль CPU при записи голосов, цель 150 RPS

| Компонент | CPU |
|---|---|
| Приложение (gunicorn) | 130–150 % |
| PostgreSQL | **106–116 %** |
| Redis | 1–5 % |
| Генератор k6 | 9–15 % |

Суммарно ~270 % из 800 % доступных. **Система не упиралась в CPU** — значит
ограничитель был в другом месте.

### 3.4. Ожидания в базе

Шесть срезов `pg_stat_activity` в пике:

```
Client | ClientRead | 1–4
(running)           | 1–2
```

Ни одного `Lock`, ни одного `LWLock`: **advisory-локи этапа 2 не создают
конкуренции**. Зато преобладает `ClientRead` — backend PostgreSQL сидит внутри
открытой транзакции и ждёт, когда приложение пришлёт следующий оператор.

### 3.5. Профиль CPU приложения — что нашлось

py-spy по воркеру gunicorn под нагрузкой. В выборке стеков многократно:

```
_parse_conninfo (psycopg/conninfo.py:101)
make_conninfo  (psycopg/conninfo.py:62)
connect        (psycopg/connection.py:107)
get_new_connection (django/db/backends/postgresql/base.py:332)
ensure_connection  (django/db/backends/base/base.py:279)
```

Приложение **открывало новое соединение с PostgreSQL внутри обработки
запроса**. Причина — `CONN_MAX_AGE=0`: Django закрывает соединение после
каждого HTTP-запроса, и на следующий PostgreSQL заново порождает
backend-процесс.

Это же объясняет 3.3 и 3.4: PostgreSQL жёг больше 100 % CPU, выполнив за 100
секунд запросов всего на несколько секунд. CPU уходил не в запросы, а в
создание процессов.

## 4. Проверка гипотезы: A/B

Настройка `CONN_MAX_AGE=0` появилась на этапе 7 **осознанно** — она обязательна
за PgBouncer в transaction pooling (ТЗ п.13). Но на стенде PgBouncer нет, и
получилось худшее из двух: пулера нет и переиспользования соединений тоже нет.

Два прогона, всё идентично — те же данные, тот же профиль, та же цель 150 RPS,
90 секунд, различается одна переменная:

| | A: `CONN_MAX_AGE=0` | B: `CONN_MAX_AGE=60` |
|---|---|---|
| Принято голосов | 13 477 | 14 306 |
| Записей в секунду | 134.7 | **143.0** |
| Медиана | 17.24 мс | **4.15 мс** |
| p95 | **363.9 мс** | **13.1 мс** |
| Среднее | 76.23 мс | 11.83 мс |
| Не уложились в темп | 847 | **18** |
| Ошибок 5xx | 0 | 0 |
| Время базы на голос | 1.28 мс | **0.232 мс** |
| Целостность данных | подтверждена | подтверждена |

**p95 упал в 28 раз.** Пропускная способность выросла всего на 6 % только
потому, что вариант B почти достиг заданной цели 150/с и упёрся в неё, а не
в себя.

Показательна последняя строка: те же девять запросов стали исполняться в базе
**в 5.5 раза быстрее**. Сами запросы не менялись — менялось то, насколько
сервер был занят порождением процессов.

### Где оказался потолок варианта B

Тот же профиль, цель 400 RPS:

| Принято голосов | Записей в секунду | p95 | Ошибок 5xx | Целостность |
|---|---|---|---|---|
| 19 997 | **285.7** | 173.7 мс | 0 | подтверждена |

Это **не потолок системы**: закончился пул из 20 000 студентов — все
проголосовали. Попытка взять пул больше упёрлась в память генератора:
k6 не пережил файл с 40 000 токенов при 3.8 GiB на все контейнеры.
**Ограничителем стал стенд, а не приложение** (ТЗ п.109).

Профиль CPU при этой нагрузке изменился качественно:

| Компонент | было (150 RPS, A) | стало (~400 RPS, B) |
|---|---|---|
| Приложение | 130–150 % | **233–292 %** |
| PostgreSQL | 106–116 % | **65–77 %** |
| Генератор k6 | 9–15 % | 19–257 % |

PostgreSQL при **втрое большей** нагрузке стал тратить **меньше** CPU.
В ожиданиях впервые появился `IO | WALSync` — то есть база наконец дошла
до того, чем и должна быть занята: фиксацией журнала на диск.

## 5. Решения

| Кандидат | Условие, при котором делаем | Показало | Решение |
|---|---|---|---|
| Переиспользование соединений с базой | Профилировщик показывает установление соединения в горячем пути | Да, стеки в `psycopg.connect`; A/B дал p95 364 → 13 мс | **Сделано** — см. 5.1 |
| Сократить 9 round trips в `cast_secret_ballot` | Обмен с базой остаётся ограничителем | Нет: после 5.1 база тратит 0.232 мс на голос и 65–77 % CPU, ограничитель переехал в приложение | **Не делаем** — см. 5.2 |
| Убрать SAVEPOINT через `ON CONFLICT DO NOTHING` | SAVEPOINT заметен в профиле | Нет: 2 round trips из 9, в профиле базы не выделяется | **Не делаем** |
| Новый индекс по данным `pg_stat_statements` | В топе запрос с seq scan | Нет: весь топ — точечные обращения по первичным и уникальным ключам | **Не делаем** |
| Подбор числа воркеров и потоков gunicorn | CPU приложения упирается в предел при недогруженной базе | Условие выполнено, но измерить нельзя: генератор берёт до 257 % на тех же 8 ядрах | **Отложено до реальной инфраструктуры** |

### 5.1. Что сделано

Значение `CONN_MAX_AGE=0` по умолчанию **оставлено без изменений**. Оно верно
для схемы с PgBouncer, которую ТЗ п.13 называет обязательной, и менять
умолчание значило бы молча сломать правильное развёртывание.

Вместо этого развёртывание обязано заявить схему явно:

```
Схема 1 (рекомендуемая, ТЗ п.13):  DB_BEHIND_PGBOUNCER=True,  DB_CONN_MAX_AGE=0
Схема 2 (без пулера):              DB_BEHIND_PGBOUNCER=False, DB_CONN_MAX_AGE=60
```

Проверка `check_conn_max_age` в `apps/core/system_checks.py` не пропускает
деплой при несогласованной паре и ловит **обе** ошибки: и соединение на каждый
запрос без пулера, и persistent-соединения за пулером, которые ломают сам
пулинг. Подсказка называет оба выхода и приводит измеренные числа — она
пишется для человека, который читает её в CI, а не для того, кто уже знает
ответ.

Причина такого решения: Django не может определить наличие пулера
самостоятельно — PgBouncer выглядит для него обычным сервером PostgreSQL.
Единственный надёжный способ — потребовать явного заявления.

### 5.2. Почему `cast_secret_ballot` не переписан

Роадмап разрешает PostgreSQL-specific реализацию (CTE, database function)
при условии, что **обмен с базой остаётся узким местом**. После 5.1 это
условие не выполняется:

- все девять обращений вместе исполняются за **0.232 мс** на голос;
- PostgreSQL при нагрузке ~400 RPS занимает 65–77 % CPU, приложение — 233–292 %;
- в ожиданиях базы нет ни блокировок, ни давления round trips.

Переписывать сейчас значило бы усложнять горячий путь голосования без
доказательств — ровно то, что ТЗ п.84 и п.120 запрещают. Инварианты ТЗ п.5, 6,
10 обеспечиваются текущей реализацией, и риск их нарушить реален, а выигрыш —
нет.

**Условие пересмотра:** если на боевой инфраструктуре с сетью между приложением
и базой (RTT 0.3–1 мс) профилирование покажет, что девять round trips
доминируют в задержке голосования, решение меняется. Измерение для этого уже
есть: `tests/performance/test_query_budget_vote.py` фиксирует число, а
`pg_hot_statements` покажет долю.

## 6. Оставшийся ограничитель

**На этом железе — сам стенд.** Генератор нагрузки берёт до 257 % CPU на тех же
восьми ядрах, что приложение и база, а объём фикстур ограничен памятью
контейнера. Цифра 285.7 записи в секунду — это **нижняя граница**, полученная
до того, как закончились студенты, а не потолок системы.

**В приложении — CPU приложения.** После устранения накладных расходов на
соединения PostgreSQL перестал быть ограничителем: 65–77 % CPU против 233–292 %
у приложения, и только теперь в базе появилось ожидание `WALSync`, то есть
настоящая работа по фиксации журнала.

**Что нужно измерить на реальной инфраструктуре, чтобы двигаться дальше:**

1. Генератор нагрузки на **отдельной машине** — иначе все цифры занижены.
2. Приложение и PostgreSQL на **разных машинах** — появится сеть, и цена
   девяти round trips станет видна. Только это измерение может оправдать
   переписывание `cast_secret_ballot`.
3. Профиль CPU приложения под нагрузкой, когда за ядра никто не конкурирует, —
   тогда имеет смысл подбирать число воркеров и потоков gunicorn.
4. Диск боевого сервера: `WALSync` уже проявился, и на настоящем объёме записи
   именно он может стать ограничителем, а не CPU.

## 7. Чего эти измерения не доказывают

- Абсолютные значения RPS получены на ноутбуке и **не подтверждают SLO
  из ТЗ п.85**. Ступени 10k / 20k / 40k здесь не проверялись и не заявляются.
- Сравнение A/B честно **только внутри одного железа**: доказано, что
  переиспользование соединений даёт 28-кратное улучшение p95 при прочих равных.
  Насколько велика будет разница на другой машине — здесь не измерено.
- Профиль записи голосов даёт худший случай для кэша личности: каждый студент
  голосует один раз, поэтому каждый — промах кэша. В реальной эксплуатации
  студент делает несколько запросов, и доля этого запроса будет ниже.
- Шесть срезов `pg_stat_activity` — выборка, а не непрерывное наблюдение:
  редкие события блокировок она могла не поймать. Утверждение «нет конкуренции
  за advisory-локи» опирается также на `deadlocks=0` за всё время прогонов
  и на concurrency-тесты этапа 2.
