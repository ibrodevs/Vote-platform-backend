# Нагрузочное тестирование

Требования ТЗ п.77–82, 108–112. Результаты прогонов — в
[PERFORMANCE.md](PERFORMANCE.md) раздел 5.

---

## Главное предупреждение

**Цифры, полученные на машине разработчика, не подтверждают SLO из ТЗ п.85.**
Генератор нагрузки, приложение и база делят одни и те же ядра, а Docker
здесь располагает 3.8 ГБ памяти на всё. ТЗ п.109 прямо предупреждает, что
один ноутбук сам становится узким местом.

Сценарии написаны с **параметризуемым** целевым RPS, включая ступени
1k → 5k → 10k → 20k → 40k из ТЗ п.79. Они готовы к запуску на настоящей
инфраструктуре; здесь прогоняется тот масштаб, который железо выдерживает.

Писать «поддерживает 40k RPS» без прогона на такой инфраструктуре
запрещено ТЗ п.123 — и в этом репозитории такого утверждения нет.

## Подготовка

```bash
# 1. Данные. Голоса не создаются: их создаст сам прогон
docker compose exec web python manage.py generate_test_data \
    --universities 10 --students 60000 --elections 20 \
    --candidates-per-election 8 --vote-ratio 0.0

# 2. Токены. Логин внутри k6 недопустим: проверка пароля через pbkdf2
#    сама по себе тяжёлая, и профиль мерил бы её
docker compose exec web python manage.py export_loadtest_fixtures --students 5000
```

**Ключ подписи должен совпадать.** Токены выпускаются тем же
`DJANGO_SECRET_KEY`, с которым работает цель. Иначе все запросы вернут 403,
и это легко принять за поломку приложения.

**Лимиты частоты выключаются:** `RATE_LIMIT_ENABLED=False`. Иначе прогон
измеряет троттлер (ТЗ п.36).

## Запуск

```bash
./loadtests/run.sh profile_a_public_read
TARGET_RPS=500 DURATION=60s ./loadtests/run.sh profile_c_mixed
```

`run.sh` делает три шага, и третий не опционален:

1. фиксирует окружение (ТЗ п.108);
2. прогоняет сценарий;
3. **проверяет целостность данных** — ТЗ п.87: нагрузка без этой проверки
   не считается валидным бенчмарком.

### Почему профиль D отдельный

40k HTTP RPS и 40k записей голосов в секунду — **разные величины**.
Один голос создаёт две строки плюс записи в индексы и WAL, и всё это
фиксируется на диске до ответа клиенту. Максимальная скорость записи
упирается в WAL и IOPS, а не в CPU приложения, и измеряется отдельно.

В профиле D каждый студент голосует **ровно один раз**: повторные попытки
возвращали бы `already_voted`, который стоит дешевле настоящей записи
и завысил бы результат в разы.

### Студент и выборы — одного вуза

Сценарии подбирают выборы университета студента (`pickEligible`).
Без этого подавляющее большинство запросов возвращает `ineligible_student`,
профиль мерит скорость отказов — и выглядит успешным, потому что 400
не является ошибкой сервера. Эта ошибка была допущена при первом прогоне
и исправлена: принятых голосов стало 231 вместо 23.

## Проверка, что генератор не узкое место (ТЗ п.109)

Во время прогона:

```bash
docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}'
```

Если k6 упирается в потолок CPU — измеряется он, а не приложение,
и нужны распределённые генераторы.

## Обязательно после прогона

```bash
docker compose exec web python manage.py verify_election_integrity
```

Проверяется: совпадение числа записей об участии и бюллетеней, отсутствие
дублей, осиротевших бюллетеней и голосов от студентов чужого вуза.
Команда **не сопоставляет студента с кандидатом** — это разрушило бы
тайну голосования, ради которой всё строилось (ТЗ п.115).

Фикстуры содержат действующие JWT и в Git не попадают.
