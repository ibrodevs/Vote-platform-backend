# Производительность

Документ наполняется по этапам. Сейчас здесь **только измеренные числа запросов**.
Пропускная способность, задержки и максимальный RPS появятся после этапа 10 —
до тех пор никаких утверждений о производительности в проекте нет и быть не должно
(ТЗ п.85, 123).

## 1. Бюджет SQL-запросов (этап 4)

**Метод.** Каждый endpoint вызывается дважды на двух наборах данных; учитывается
второй вызов, чтобы кэш личности студента был прогрет и измерялась стоимость
запроса, а не промаха. Считаются только содержательные запросы: `SAVEPOINT`,
`RELEASE`, `BEGIN`, `COMMIT` и advisory-локи исключены как служебная обвязка.

**Окружение.** PostgreSQL 16.15 в Docker, Django 5.2.17, коммит этапа 4.

**Наборы данных.**
Малый — 2 выборов × 3 кандидата, 5 студентов.
Большой — 5 выборов × 10 кандидатов, 20 студентов (для результатов — 25 кандидатов).

### Результат

| Endpoint | До: малый | До: большой | После: малый | После: большой |
|---|---|---|---|---|
| `GET /elections/available/?all=true` | 12 | **62** | 3 | **3** |
| `GET /admin/students/` | 14 | **44** | 3 | **3** |
| `GET /admin/elections/{id}/results/` | 8 | **30** | 5 | **5** |
| `POST /admin/elections/{id}/results/export/` | 8 | **30** | 5 | **5** |
| `GET /admin/elections/` | 7 | 17 | 3 | **3** |
| `GET /elections/{id}/` | 5 | 12 | 2 | **2** |
| `GET /admin/universities/` | 6 | 9 | 4 | **4** |
| `GET /elections/recent/` | 3 | 3 | 2 | **2** |
| `GET /admin/elections/{id}/turnout/` | 4 | 4 | 4 | **4** |
| `POST /voting/cast/` | 4 | 4 | 4 | **4** |
| `GET /voting/status/{id}/` | 1 | 1 | 1 | **1** |

**Главное здесь не абсолютные числа, а отсутствие роста.** До этапа 4 семь
endpoint'ов дорожали вместе с данными; теперь ни один не дорожает — числа
в двух последних колонках совпадают полностью.

### Что именно было исправлено

| Причина | Где | Исправление |
|---|---|---|
| `prefetch_related`, которым никто не пользуется | `StudentSerializer` | `exists()`, `count()` и `order_by()` игнорируют prefetch-кэш и всегда идут в базу. Заменены на `Count(distinct=True)` и `Max(...)` |
| `1+N` подсчётов голосов | `results/`, `results/export/` | один `values('candidate_id').annotate(Count('id'))` |
| `obj.candidates.count()` на объект | `ElectionSerializer` | `annotate(Count('candidates', distinct=True))` |
| вложенные кандидаты без prefetch | `available/`, `elections/{id}/` | `Prefetch('candidates', queryset=...select_related('university', 'election'))` |
| `election.title` и `university.name` на кандидата | списки кандидатов | `select_related('election', 'university')` |
| два `COUNT` на университет | `UniversitySerializer` | `Count(..., filter=Q(...), distinct=True)` |

**Почему аннотация, а не prefetch, там где нужен только счётчик.** Prefetch тоже
убирает N+1, но тянет по сети сами строки. На списке из 50 выборов по 20 кандидатов
ради одного числа приехала бы 1000 лишних строк.

**Почему `distinct=True` обязателен.** Фильтр `?voted=` и два счётчика в
`UniversitySerializer` делают JOIN; без `distinct` строки перемножаются
и счётчики завышаются.

### Устранённое расхождение

`turnout/` считал проголосовавших по `VoteRecord`, а `results/` — по `Ballot`,
двумя независимыми копиями кода. Числа обязаны совпадать (иначе нарушен
инвариант атомарности из ТЗ п.5), но разойтись могли незаметно. Теперь обе
вьюхи и экспорт используют `apps/elections/aggregates.py`.

### Чего здесь сознательно нет

- **Счётчика-строки.** ТЗ п.30 прямо запрещает `election.vote_count += 1`
  и `ElectionStats.total_votes`: это возвращает сериализацию всех голосов
  через одну строку, ровно то, что убирал этап 2.
- **Кэширования.** `eligible_voters_count` и явка считаются точно, из PostgreSQL.
  Кэш явки — этап 6, и источником истины он не станет.

## 2. Ограничение размера страницы (ТЗ п.93)

До этапа 4 `page_size_query_param` не был задан вовсе: клиент не мог менять
размер страницы, а любой список отдавал ровно 20 записей.

Теперь `apps/core/pagination.py`: `page_size` = 20 по умолчанию,
`page_size_query_param` = `page_size`, `max_page_size` = 200.
Запрос `?page_size=1000000` усекается до потолка, а не выгружает таблицу целиком.

## 3. EXPLAIN ANALYZE горячих запросов (этап 5)

**Метод.** `EXPLAIN (ANALYZE, BUFFERS)` по фиксированному списку запросов,
выведенному из реального кода. Команда: `python manage.py explain_hot_queries`.

**Окружение.** PostgreSQL 16 в Docker. Данные сгенерированы
`python manage.py generate_test_data --students 200000 --elections 60`:
200 000 студентов, 180 000 голосов, 600 кандидатов, 60 выборов, 20 вузов.

**Почему нужен такой объём.** На таблице в 19 строк планировщик всегда выбирает
Seq Scan — прочитать одну страницу дешевле, чем идти в индекс. Любой вывод об
индексах, сделанный на demo-данных, был бы неверным.

### Результат

| Запрос | План до | Время до | План после | Время после |
|---|---|---|---|---|
| **login по email** (`iexact`) | Parallel Seq Scan, 5771 буферов | **29.6 ms** | Index Scan, 4 буфера | **0.04 ms** |
| **identify по коду студента** | Bitmap Heap Scan, 5780 буферов | **8.7 ms** | Index Scan, 3 буфера | **0.04 ms** |
| **число избирателей** (`COUNT`) | Bitmap Heap Scan, 5780 буферов | **12.9 ms** | Index Only Scan, 11 буферов, Heap Fetches 0 | **0.88 ms** |
| turnout / явка | Bitmap + Index Scan | 0.96 ms | Index Only Scan | 0.90 ms |
| vote status | Index Scan | 0.06 ms | Index Scan | 0.06 ms |
| available / где голосовал | Bitmap + Index Scan | 0.10 ms | Bitmap + Index Scan | 0.17 ms |
| results / агрегация | Bitmap + Index Scan | 1.23 ms | Bitmap + Index Scan | 1.90 ms |
| auth, промах кэша | Index Scan | 0.03 ms | Index Scan | 0.05 ms |
| admin, список кандидатов | Bitmap + Index Scan | 0.05 ms | Bitmap + Index Scan | 0.16 ms |
| vote / выбор выборов | Seq Scan (60 строк) | 0.02 ms | Seq Scan | 0.02 ms |
| vote / проверка кандидата | Seq Scan (600 строк) | 0.08 ms | Seq Scan | 0.20 ms |
| available / активные выборы вуза | Seq Scan (60 строк) | 0.02 ms | Seq Scan | 0.03 ms |
| admin, поиск студентов | Seq Scan, 6223 буфера | 69.5 ms | Seq Scan | 69.6 ms |

Расхождения в доли миллисекунды на уже быстрых запросах — шум измерения,
а не регрессия: там, где время меньше 1 мс, разброс между прогонами сопоставим
с самой величиной.

### Добавленные индексы — каждый по конкретному плану

| Индекс | Какой запрос чинит | Доказательство |
|---|---|---|
| `student_email_upper_idx` на `Upper(email)` | логин по email | Seq Scan → Index Scan, 5771 → 4 буфера |
| `student_uni_code_upper_idx` на `(university, Upper(student_id))` | identify студента | 10 000 строк из индекса, все отброшены фильтром → прямое попадание |
| `student_uni_active_idx` на `(university, is_active)` | число избирателей | чтение 5771 блока кучи → Index Only Scan, Heap Fetches 0 |

**Индексы строятся `CREATE INDEX CONCURRENTLY`** (ТЗ п.54) через
`apps/core/migration_operations.AddIndexSafely`: обычный `CREATE INDEX` берёт
блокировку SHARE и на миллионе студентов остановил бы запись на десятки секунд,
включая приём голосов — `VoteRecord` ссылается на студента внешним ключом.

### Чего сознательно НЕ добавлено

**Индексов на `elections` и `candidates`.** Seq Scan там — правильный выбор
планировщика: в таблицах 60 и 600 строк, и запросы отрабатывают за 0.02–0.2 мс.
Индекс здесь только замедлил бы запись. ТЗ п.14 прямо требует добавлять индексы
«только там, где они действительно используются».

**Trigram-индексов для админского поиска.** Вариант `pg_trgm` + GIN по выражению
`UPPER(field::text)` построен и измерен:

| Сценарий | Без индекса | С trigram |
|---|---|---|
| селективный запрос внутри вуза (реальный случай) | 10 мс | 10 мс |
| селективный запрос по всем 200 000 | 44 мс | **17 мс** |
| НЕселективный запрос (7571 совпадение) | 48 мс | **73 мс — хуже** |
| `bulk_create` 20 000 студентов | 1.21 с | **2.27 с (+88%)** |
| размер индексов | — | **+22 МБ** на таблицу в 48 МБ |

Почти двукратное замедление импорта студентов — прямой ущерб требованию ТЗ п.41,
а выигрыш достаётся сценарию, который в реальном случае и так укладывается
в 10 мс. Вместо индекса поиск ограничен снизу по длине (см. ниже).
Решение пересматривается по данным этапа 10.

**Важно про Index Only Scan.** Он требует актуальной карты видимости, которую
поддерживает `VACUUM`. Сразу после массовой загрузки или пересоздания индекса
карта пуста, и тот же запрос падает обратно на Bitmap Heap Scan: измерено
10.6 мс до `VACUUM ANALYZE` и 0.88 мс после. В установившемся режиме это делает
autovacuum; после `loaddata` или перестройки индексов `VACUUM ANALYZE` нужно
запустить вручную.

### Ограничение поиска (ТЗ п.94)

`apps/core/filters.MinLengthSearchFilter`: запросы короче 3 символов
игнорируются. Поиск по одному символу совпадает почти со всей таблицей —
полный скан при нулевой пользе. Запрос именно игнорируется, а не отвергается
ошибкой: пользователь набирает строку по символу.

### Уникальность email (ТЗ п.15)

`UniqueConstraint(Lower('email'))` с условием «email не пуст и не NULL».
Регистрация проверяла `exists()` перед `INSERT` — два параллельных запроса
проходили проверку одновременно. Констрейнт закрывает гонку; при его
срабатывании API отдаёт тот же `400 email_already_exists`, а не 500.

Частичный индекс обязателен: студентов без email в базе много (загруженные
списком), и без условия второй же такой студент нарушил бы уникальность.

Миграция `0006` содержит guard: при существующих дубликатах она **падает
с перечислением конфликтующих записей и инструкцией**, ничего не изменяя.
ТЗ п.15 прямо запрещает чинить такие данные автоматически.
