# Runbook: бэкапы, восстановление, откат, инциденты

Документ для того, кто эксплуатирует систему, а не пишет её. Команды здесь
можно выполнять, не читая исходный код.

**Пункты ТЗ:** 47, 99, 100.

## 1. Бэкапы

### 1.1. Ежедневная копия

```bash
BACKUP_DIR=/mnt/backups ./scripts/backup.sh
```

Формат `pg_dump -Fc`: сжатый, восстанавливается параллельно, позволяет
достать отдельную таблицу.

Скрипт **отказывается** считать успехом дамп меньше 10 КБ или файл, который
не читается `pg_restore --list`. Молча созданный нулевой дамп — худший вид
бэкапа: он выглядит как сделанный.

Хранение по умолчанию — 14 дней (`RETENTION_DAYS`). Копии должны лежать
**не на том же диске**, что база: отказ диска не должен уносить и данные,
и их резервную копию.

cron:

```cron
15 3 * * * cd /srv/vote-platform && BACKUP_DIR=/mnt/backups ./scripts/backup.sh >> /var/log/vote-backup.log 2>&1
```

### 1.2. Проверка копии восстановлением — обязательна

**Копия, из которой никто не восстанавливался, — это предположение,
а не резервная копия.** ТЗ п.47 требует именно регулярного restore test.

```bash
./scripts/verify_backup.sh /mnt/backups/vote_db-20260923-115833.dump
```

Скрипт восстанавливает дамп во **временную** базу, сверяет число строк
и проверяет целостность голосов. Рабочая база не затрагивается.

```

```

### 1.3. WAL archiving и PITR

Ежедневный дамп теряет всё, что произошло после него. В день выборов это
недопустимо: потерянные голоса восстановить неоткуда.

`postgresql.conf` на primary:

```conf
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /mnt/wal-archive/%f && cp %p /mnt/wal-archive/%f'
archive_timeout = 300          # сегмент закрывается не реже чем раз в 5 минут
max_wal_senders = 5
```

Базовая копия для PITR:

```bash
pg_basebackup -h <primary> -U replicator -D /mnt/basebackup/$(date +%F) -Fp -Xs -P
```

Восстановление на момент времени: развернуть базовую копию, положить рядом
архив WAL и указать точку:

```conf
restore_command = 'cp /mnt/wal-archive/%f %p'
recovery_target_time = '2026-09-23 14:31:00+06'
recovery_target_action = 'promote'
```

**Точка восстановления выбирается по журналу приложения**, а не наугад:
записи `vote_accepted` в JSON-логах дают время последнего принятого голоса.

**Проверьте архив до дня выборов.** `archive_command`, который молча
не работает, обнаруживается ровно тогда, когда он нужен.

## 2. Восстановление базы

**Эта процедура уничтожает текущую базу.**

```bash
# 1. Остановить приложение и Celery — иначе восстановление смешается
#    с новыми записями
systemctl stop vote-web vote-celery

# 2. Восстановить
./scripts/restore.sh /mnt/backups/vote_db-20260923-115833.dump

# 3. Обязательная проверка
python manage.py migrate --check
python manage.py verify_election_integrity

# 4. Запустить обратно
systemctl start vote-web vote-celery
```

Скрипт перед разрушением снимает **страховочную копию** текущего состояния
в `/tmp/pre-restore-<база>-<время>.dump`: восстановление из неверного дампа —
обычная ошибка, и откатить её должно быть чем.

Процедура проверена целиком 2026-09-23, включая разрушающий шаг: после
восстановления `verify_election_integrity` подтвердил 12 записей об участии
и 12 бюллетеней без расхождений.

## 3. Откат релиза

Порядок обратный развёртыванию. Код откатывается всегда, миграции — нет.

```bash
# 1. Вернуть предыдущий образ
docker compose -f docker-compose.prod.yml up -d --no-deps web

# 2. Проверить
curl -fsS https://<домен>/health/ready
python manage.py production_check
```

**Миграции откатывайте только если точно знаете, что откатываете.**
Миграция, удаляющая колонку, при откате уничтожит данные. Все миграции
этого проекта аддитивны и совместимы с предыдущей версией кода — именно
поэтому откат кода безопасен сам по себе.

Если откатить миграцию всё же нужно:

```bash
python manage.py migrate <приложение> <номер_предыдущей>
```

## 4. Инциденты

### 4.1. Redis недоступен

**Голосование продолжает работать.** Redis — ускоритель, не источник истины
(ТЗ п.114). Что изменится: аутентификация пойдёт в PostgreSQL на каждый
запрос, статус голосования — тоже, нагрузка на базу вырастет, задержки
вырастут. Голоса не теряются и не дублируются.

```bash
redis-cli -h <redis> ping
curl -fsS https://<домен>/health/ready    # покажет cache_available: false
```

Полная очистка Redis **не меняет ни одного зафиксированного голоса** —
это проверено тестами.

### 4.2. Реплика отстаёт

Голосование не затронуто: все критичные чтения идут на primary (ТЗ п.46).
Отставание влияет только на новости, FAQ, статические страницы и справочник
вузов.

```sql
SELECT now() - pg_last_xact_replay_timestamp() AS lag;
```

Если отставание велико, уберите `DB_REPLICA_HOST` и перезапустите
приложение: всё вернётся на primary.

### 4.3. Приложение упало на одной ноде

Балансировщик перестаёт слать на неё трафик по `/health/ready`. Sticky
sessions не используются, состояния в процессе нет — пользователи ничего
не заметят.

```bash
curl -fsS http://<нода>:8000/health/live     # процесс жив
curl -fsS http://<нода>:8000/health/ready    # готов принимать трафик
```

### 4.4. Подозрение на проблему с данными

```bash
python manage.py verify_election_integrity
```

Проверяет: число `VoteRecord` и `Ballot`, отсутствие дублей
`(выборы, студент)`, осиротевших бюллетеней, частично записанных голосов
и голосов от студентов чужого вуза.

**Это первая команда при любом сомнении в результатах выборов.**

### 4.5. Что смотреть в метриках

| Симптом | Метрика |
|---|---|
| Растут отказы голосования | `vote_attempts_total{outcome=...}` |
| Медленные ответы | `http_request_duration_seconds` |
| База перегружена | `db_errors_total`, `db_deadlocks_total` |
| Кэш не работает | `cache_operations_total{result="miss"}` |
| Очередь не разбирается | `celery_tasks_total` |

Ни одна метрика не содержит пары «студент + кандидат»: связка этих двух
идентификаторов восстанавливает выбор человека (ТЗ п.4).
