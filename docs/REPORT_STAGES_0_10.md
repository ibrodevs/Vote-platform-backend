## 5. Этап 2 — Корректность и конкуррентность голосования

**Требования ТЗ:** п.5–11, 16, 17, 52, 53, 66, 71–76, 89, 106
**Это ядро проекта.**

### Что изменилось в алгоритме

**Было:**
```
BEGIN
  SELECT * FROM elections_election WHERE id = ? FOR UPDATE   ← все голоса в очередь
  SELECT ... FROM voting_voterecord ... FOR UPDATE           ← check-then-insert
  если существует → AlreadyVoted
  INSERT VoteRecord
  INSERT Ballot
COMMIT
```

**Стало:**
```
BEGIN
  pg_advisory_xact_lock_shared(election)    ← голоса держат одновременно
  SELECT * FROM elections_election WHERE id = ?
  проверки: ACTIVE, окно времени, университет, кандидат
  SAVEPOINT
    INSERT VoteRecord   → при UNIQUE VIOLATION: rollback, AlreadyVoted
  INSERT Ballot
COMMIT
```

### Ключевые решения

| Решение | Обоснование |
|---|---|
| Shared advisory lock для голосов | держатся одновременно, голоса не ждут друг друга |
| Exclusive advisory lock для start/finish/cancel/delete | `finish` дожидается начатых голосов и не пускает новые в критическую секцию |
| Отказ от `exists()` перед INSERT | проверка проигрывает гонке; заодно на один SQL меньше |
| Savepoint вокруг INSERT | без него `IntegrityError` оставлял транзакцию PostgreSQL в broken state |
| Ключ лока через `blake2b`, не `hash()` | встроенный `hash()` рандомизирован между процессами — воркеры получали бы разные ключи, и лок молча не работал бы |

### Concurrency-тесты (ТЗ п.72–75)

| Тест | Сценарий | Результат |
|---|---|---|
| п.72 | 1 студент, 100 параллельных попыток | ровно 1 `VoteRecord` и 1 `Ballot` |
| п.73 | 1000 студентов, 10 кандидатов | все 1000 приняты, 0 deadlock'ов |
| п.74 | голоса параллельно с `finish` | после коммита finish голоса не принимаются, частичных записей нет |
| п.75 | 1 студент одновременно за A и B | ровно 1 бюллетень |

Проверено при **100 и 200 одновременных соединениях** — 0 deadlock'ов.

### Стражи против регрессии

Два теста защищают от возврата `select_for_update`: статический по исходнику
и поведенческий (два голоса пересекаются во времени). **Оба проверены
на способность падать:** со старым кодом падают, с новым проходят за 0.25 с.

### Найдено по ходу

**D-09 — масштаб проблемы был больше, чем в ТЗ.** Замер показал:
`FOR UPDATE` на строке выборов блокирует в PostgreSQL **любую** вставку
строки с внешним ключом на эти выборы, потому что конфликтует
с `FOR KEY SHARE`. Сериализовались не только голоса между собой.

**Определение дубля зависело от СУБД.** Имя констрейнта есть в сообщении
PostgreSQL, но не SQLite. Сделано двухуровневым: `diag.constraint_name`
и имена колонок. Считать любой `IntegrityError` дублем нельзя — нарушение
FK превратилось бы в «вы уже проголосовали».

## 7. Этап 4 — Устранение N+1

**Требования ТЗ:** п.25, 26, 27, 28, 30, 48, 51, 93

### Измерено до и после

| Endpoint | До (малый → большой) | После |
|---|---|---|
| `/elections/available/?all=true` | 12 → **62** | 3 → **3** |
| `/admin/students/` | 14 → **44** | 3 → **3** |
| `/admin/elections/{id}/results/` | 8 → **30** | 5 → **5** |
| `POST .../results/export/` | 8 → **30** | 5 → **5** |
| `/admin/elections/` | 7 → 17 | 3 → **3** |
| `/elections/{id}/` | 5 → 12 | 2 → **2** |
| `/admin/universities/` | 6 → 9 | 4 → **4** |

Масштабы: 2 выборов × 3 кандидата × 5 студентов против 5 × 10 × 20.
**Главное — числа в последней колонке совпадают: роста нет.**

### Причины и исправления

| Причина | Исправление |
|---|---|
| `prefetch_related`, которым никто не пользуется: `exists()`, `count()` и `order_by()` игнорируют prefetch-кэш | `Count(distinct=True)` и `Max()` |
| `1+N` подсчётов голосов | один `values('candidate_id').annotate(Count('id'))` |
| `obj.candidates.count()` на объект | `annotate` — для счётчика не нужно тянуть строки |
| Вложенные кандидаты без prefetch | `Prefetch(..., select_related('university', 'election'))` |
| Два `COUNT` на университет | `Count(filter=Q(...), distinct=True)` |

### Устранённое расхождение

`turnout/` считал явку по `VoteRecord`, а `results/` — по `Ballot`, двумя
независимыми копиями кода. Числа обязаны совпадать (инвариант атомарности),
но разойтись могли молча. Вынесено в `apps/elections/aggregates.py`.

### Найдено по ходу

**Три моих теста были пустышками.** Тесты «не растёт» сравнивали `?page_size=2`
с обычным запросом, но `page_size_query_param` не был задан вовсе — параметр
игнорировался, и оба вызова были идентичны. Теперь тест сначала проверяет,
что `page_size` действует.

**Пагинация не имела потолка.** Добавлен `max_page_size=200`: `?page_size=1000000`
усекается, а не выгружает таблицу студентов одним ответом.

## 8. Этап 5 — Индексы

**Требования ТЗ:** п.14, 15, 54, 78, 94

### Метод

Индексы добавлялись **только по планам `EXPLAIN (ANALYZE, BUFFERS)`**
на 200 000 студентов и 180 000 голосов. На 19 строках планировщик всегда
выбирает Seq Scan, и любой вывод был бы неверным — поэтому сначала был
написан генератор синтетических данных.

### Результат

| Запрос | До | После |
|---|---|---|
| **login по email** | Parallel Seq Scan, 29.6 мс, 5771 буфер | **Index Scan, 0.04 мс, 4 буфера** |
| **identify по коду** | Bitmap Heap Scan, 8.7 мс, 5780 буферов | **Index Scan, 0.04 мс, 3 буфера** |
| **COUNT избирателей** | Bitmap Heap Scan, 12.9 мс, 5780 буферов | **Index Only Scan, 0.88 мс, 11 буферов** |

### Чего сознательно не добавлено

**Индексов на `elections` (60 строк) и `candidates` (600).** Seq Scan там —
правильный выбор планировщика, запросы отрабатывают за 0.02–0.2 мс.
Индекс только замедлил бы запись. ТЗ п.14 требует добавлять индексы
«только там, где они действительно используются».

**Trigram-индексов для админского поиска.** Построены и измерены в обе стороны:

| Сценарий | Без индекса | С trigram |
|---|---|---|
| селективный поиск внутри вуза (реальный случай) | 10 мс | 10 мс |
| селективный по всем 200k | 44 мс | **17 мс** |
| неселективный (7571 совпадение) | 48 мс | **73 мс — хуже** |
| `bulk_create` 20 000 студентов | 1.21 с | **2.27 с (+88%)** |
| размер | — | **+22 МБ** на таблицу в 48 МБ |

Почти двукратное замедление импорта — прямой ущерб требованию п.41,
а выигрыш достаётся сценарию, который и так укладывается в 10 мс.
Вместо индекса — ограничение минимальной длины поиска (3 символа).

### Уникальность email (ТЗ п.15)

`UNIQUE(LOWER(email))` с частичным условием закрывает гонку при регистрации.
Миграция при существующих дубликатах **падает с перечислением и инструкцией**,
ничего не изменяя — ТЗ прямо запрещает чинить такие данные автоматически.

### Безопасные миграции (ТЗ п.54)

Индексы строятся `CREATE INDEX CONCURRENTLY` через `AddIndexSafely`:
обычный `CREATE INDEX` берёт блокировку SHARE и на миллионе студентов
остановил бы запись, включая приём голосов.

### Операционная находка

**Index Only Scan требует актуальной карты видимости.** После пересоздания
индексов тот же запрос дал 10.6 мс вместо 0.88 — помог `VACUUM ANALYZE`.
Записано в README и в процедуру миграции.

| `GET results` — завершённые | 5 | **2** |
| `GET vote status` — не голосовал | 1 | 1 *(намеренно)* |

### Три решения, которые важнее цифр

**Отрицательный статус не кэшируется вовсе.** Устаревшее «не голосовал»
после успешного голоса показало бы студенту кнопку голосования повторно —
худший баг в этой системе. Цена отказа — один индексный запрос на 0.06 мс.

**Итоги кэшируются только у завершённых выборов.** Кэш незавершённых пережил бы
смену состояния и мог бы отдать цифры, которые уже нельзя показывать.
Ключи явки и результатов раздельные.

**`POST /vote` кэшу не доверяет.** Отдельный тест кладёт в кэш заведомо
устаревший статус «активны» и проверяет, что завершённые выборы всё равно
отклоняют голос.

### Обязательный тест ТЗ п.114

Полная очистка Redis не меняет ни одного голоса — проверено и тестом,
и вживую с остановленным контейнером. Защита от дубля после очистки держится:
она на констрейнте базы, а не на кэше.

### Найдено по ходу

**Я сам внёс расхождение контракта.** При живом Redis `voted_at` возвращался
`None`, а из базы — реальная метка времени: один endpoint отдавал разное
в зависимости от состояния кэша. Заметил на живой проверке, а не в тестах —
мой тест проверял только `has_voted`. Добавлен тест, сравнивающий полные ответы.

воркеров — предмет бенчмарка, а не вкуса.

## 11. Этап 8 — Безопасность

**Требования ТЗ:** п.34, 35, 36, 67, 98

### D-05 оказался хуже, чем в реестре

Код подтверждения не только хранился открытым в базе — он писался
**и в `logger.info`, и в `print`** вместе с телефоном и `student_id`.
Любой с доступом к логам мог войти под этим студентом.

Теперь: хэш в базе, в логе только id сессии и две последние цифры номера,
в ответе код возвращается только при `DEBUG=True`. Миграция гасит открытые
сессии явно, а не роняет студентов в «неверный код».

### Две разные гонки в OTP, а не одна

| Гонка | Последствие | Исправление |
|---|---|---|
| `attempts += 1; save()` терял попытки | перебор кода обходил лимит | `F('attempts') + 1` |
| Два параллельных запроса с верным кодом **оба** проходили проверку | оба выдавали токен | условный `UPDATE ... WHERE is_verified = false` |

Проверено тестом на 10 параллельных запросов: **ровно один успех**.

### Rate limiting с ключом по студенту

Главная опасность здесь — не пропустить атаку, а **заблокировать университет**:
за одним внешним IP сидят тысячи студентов (ТЗ п.36).

| Endpoint | Ключ | Обоснование |
|---|---|---|
| Голосование, статус | **студент** | IP не участвует вовсе |
| Логин, регистрация, OTP | IP | студента ещё нет, а перебор идёт с одного адреса |

Тест: 40 студентов с одного адреса голосуют все до одного; один студент
с 30 попытками упирается в свой лимит.

Лимиты отключаются переменной — иначе бенчмарк измерял бы троттлер.

## 12. Этап 9 — Наблюдаемость

**Требования ТЗ:** п.61, 62, 63, 64

### Логи

JSON в production, пример из работающего контейнера:

```json
{"ts":"2026-09-20T23:01:30+0600","level":"INFO","logger":"apps.core.access",
 "message":"request","instance":"e2c843d4e137","request_id":"c36a1b4d-...",
 "method":"POST","route":"/api/v1/voting/cast/","status":200,"duration_ms":145.0}
```

`route` — **шаблон** маршрута, а не путь с подставленным id: иначе
кардинальность метрик взрывается, и в лог попадает, какие именно выборы
смотрел запрос.

Приватность обеспечивается механизмом: `SensitiveDataFilter` вырезает
запрещённые ключи из любой записи, `scrub_text` — токены из свободного текста.
Правило в документации соблюдают люди, фильтр — всегда.

### Метрики и приватность (ТЗ п.63)

**`candidate_id` меткой не используется.** Две причины, каждой достаточно:
счётчик по кандидату, растущий синхронно с записью об участии студента,
сужает круг до одного человека; плюс тысячи временных рядов.
**`student_id` не используется нигде.** `election_id` разрешён.

Тест обходит **весь реестр метрик** и падает при появлении запрещённой метки.

### Найдено запуском

**Production-контейнер падал в цикле.** `PROMETHEUS_MULTIPROC_DIR` задан
в образе, и `prometheus_client` обращается к директории при импорте —
раньше, чем её создавал хук gunicorn.

**Без multiprocess метрики показывали бы четверть правды.** У каждого воркера
свой реестр; скрейп попадает в один случайный. При `WEB_CONCURRENCY=4` цифры
этапа 10 были бы занижены вчетверо и выглядели бы правдоподобно.
Проверено: 40 запросов через 4 воркера дают ровно **40.0**.

## 13. Этап 10 — Нагрузочное тестирование

**Требования ТЗ:** п.77–82, 85–88, 91, 108–112, 115

### Окружение (ТЗ п.108)

| Параметр | Значение |
|---|---|
| Commit | `0944edb` |
| Django / Python | 5.2.17 / 3.11.16 |
| PostgreSQL / Redis | 16.15 / 7.4.11 |
| Хост | MacBook, 8 ядер, 8 ГБ RAM |
| Docker | 8 CPU, **3.8 ГБ RAM на всё** |
| Приложение | Gunicorn, 4 воркера × 4 потока |
| Генератор | k6 в контейнере **на той же машине** |
| Данные | 10 вузов, 60 000 студентов, 20 выборов |

### Результаты

| Профиль | Результат |
|---|---|
| A — публичные чтения | **~150 RPS**, p95 168 мс, 0% 5xx |
| B — аутентифицированные | **111 RPS**, p95 **49 мс** при SLO 300 |
| C — смешанный 55/15/15/10/5 | 92 RPS, p95 40 мс, 231 голос принят |
| D — **durable записи** | **~81 голос/с**, p95 187 мс, 0% 5xx |
| Spike 15 → 150 RPS | 0% ошибок, каскадного отказа нет |
| Soak 80 RPS, 2 минуты | дрейфа задержки нет, память стабильна |
| Deadlocks | **0** до и после всех прогонов |

### Наглядное подтверждение ТЗ п.37

Один профиль, одна цель 400 RPS:

| Сервер | Факт | p95 | Ошибки |
|---|---|---|---|
| `manage.py runserver` | 99/s | **14.53 s** | **23.26%** |
| Gunicorn 4×4 | 213/s | 2.65 s | **0%** |

### Узкое место (ТЗ п.109)

| Компонент | CPU во время прогона |
|---|---|
| Приложение | **279.7%** |
| PostgreSQL | **236.2%** |
| Redis | 5.7% |
| **k6 (генератор)** | **74.4%** |

**Генератор не является узким местом.** Упирается в CPU приложения и базы,
которые делят одни 8 ядер.

### Целостность данных (ТЗ п.87)

После каждого прогона: `VoteRecord == Ballot == 2034`, ноль дублей,
ноль осиротевших бюллетеней, ноль частично записанных голосов.
**Это главный acceptance-критерий:** цифры RPS при разъехавшихся данных
результатом не считаются.

### Найдено в собственных сценариях

**Студент и выборы подбирались независимо** — а они из разных вузов.
Почти всё возвращало `ineligible_student`, и профиль мерил скорость
**отказов**, выглядя успешным: 400 не является ошибкой сервера.
После исправления принятых голосов стало 231 вместо 23.

**Токены выпускались ключом dev-контейнера**, а цель стартовала со случайным.
Все запросы возвращали 403 — легко принять за поломку приложения.

### Оценка трафика (ТЗ п.91)

При среднем ответе ~1.8 КБ даже 40 000 RPS дают ~0.58 Гбит/с.
Сеть узким местом не станет.

- **Trigram-индексы отвергнуты** — измеренный компромисс не в их пользу

## 17. Рекомендации по развёртыванию

### Перед первым запуском — обязательно

1. **Сгенерировать новый `DJANGO_SECRET_KEY`.** Ключ из репозитория
   скомпрометирован: им подписываются студенческие JWT.
   ```
   python -c "import secrets; print(secrets.token_urlsafe(64))"
   ```
2. Заполнить `.env` по `.env.example` (105 строк с комментариями к каждой переменной)
3. Выполнить перенос базы по `docs/SQLITE_TO_POSTGRES.md`
4. `python manage.py production_check` — должен пройти все 11 проверок
5. Настроить резервное копирование **с проверкой восстановления**

### Топология

```
Nginx (TLS, rate limit, статика) → N × Gunicorn → PgBouncer → PostgreSQL
                                    Redis (кэш + брокер)
                                    Celery: default/notifications + imports/maintenance
```

### Параметры — отправная точка, не результат измерения

| Параметр | Значение | Примечание |
|---|---|---|
| `WEB_CONCURRENCY` | 4 на реплику | уточняется бенчмарком |
| `GUNICORN_THREADS` | 4 | воркер ждёт базу, а не считает |
| `DB_CONN_MAX_AGE` | **0** | обязательно при transaction pooling |
| PgBouncer `DEFAULT_POOL_SIZE` | 25 | реальных соединений к базе |
| Redis `maxmemory` | от 256 МБ | `allkeys-lru`, вытеснение безопасно |

### Первое, что стоит сделать после развёртывания

Прогнать нагрузочные сценарии на реальной инфраструктуре:

```
TARGET_RPS=5000 DURATION=5m ./loadtests/run.sh profile_c_mixed
```

Только после этого можно говорить о готовности к целевым нагрузкам.
До тех пор корректных цифр нет — и в репозитории нет ни одного
утверждения об обратном.
