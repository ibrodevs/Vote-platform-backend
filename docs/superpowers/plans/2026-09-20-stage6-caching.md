# Этап 6 — Redis-кэширование: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development
> или superpowers:executing-plans. Шаги отмечаются чекбоксами.

**Goal:** Снять с PostgreSQL повторяющиеся чтения, не сделав Redis ни источником
истины, ни точкой отказа, и не открыв скрытые результаты голосования.

**Architecture:** Кэшируется только то, что можно пересчитать из PostgreSQL.
Положительный факт участия («студент уже проголосовал») кэшируется надолго —
он необратим. Отрицательный («ещё не голосовал») не кэшируется вовсе или
кэшируется на секунды: он меняется в любой момент, и устаревшее «нет» показало бы
студенту кнопку голосования после успешного голоса. Проверка возможности
голосовать в `POST /vote` кэшу не доверяет никогда — она идёт в транзакции.

**Tech Stack:** Django cache framework + Redis (настроено на этапе 3),
`transaction.on_commit`.

**Spec:** roadmap, этап 6; ТЗ п.20, 21, 22, 23, 24, 29, 30, 51, 96, 113, 114.

---

## Global Constraints

Полный список — в roadmap. Критично здесь:

1. **Redis не источник истины (ТЗ п.114).** Полная очистка Redis не имеет права
   изменить ни один принятый голос. Это обязательный тест.
2. **`POST /vote` не доверяет кэшу.** Статус выборов и факт участия при
   голосовании проверяются в транзакции PostgreSQL. Кэш здесь только для чтения
   статуса пользователем, не для решения о приёме голоса (ТЗ п.22).
3. **Скрытые результаты остаются скрытыми (ТЗ п.51).** Кэш результатов не должен
   отдать их до завершения выборов. Ключи явки и результатов — раздельные.
4. **Никакого счётчика-строки (ТЗ п.30).** Явка считается запросом с коротким
   кэшем, а не инкрементом поля на каждый голос.
5. **Осторожно с отрицательным кэшем (ТЗ п.21).** `has_voted=false` надолго
   кэшировать нельзя.
6. **Инвалидация явная (ТЗ п.24).** TTL — вторая линия, а не основная.

### Task 2: Положительный кэш факта участия (ТЗ п.21)

**Files:** `apps/voting/services.py`, `apps/voting/views.py`

**Ключевое решение.** Кэшируется **только** положительный факт, и только
через `transaction.on_commit`: поставить его до коммита значило бы показать
студенту «вы проголосовали» при откатившейся транзакции.

Отрицательный факт не кэшируется вовсе. Обоснование: он меняется в любой
момент, а устаревшее «нет» после успешного голоса показало бы студенту
кнопку голосования повторно — худший из возможных багов в этой системе.
Цена отказа — один индексный запрос на 0.06 мс.

- [ ] **Step 1: Тест — после голоса статус читается без SQL.**
- [ ] **Step 2: Тест — при откате транзакции кэш НЕ ставится.**
- [ ] **Step 3: Реализовать `on_commit`.**
- [ ] **Step 4: Тест — очистка Redis не ломает статус (читается из БД).**
- [ ] **Step 5: Commit**

### Task 3: Кэш явки и финальных результатов (ТЗ п.28, 29)

**Files:** `apps/elections/aggregates.py`

Два разных режима, и их нельзя путать:

| Что | Когда | TTL | Почему |
|---|---|---|---|
| Явка идущих выборов | статус ACTIVE | секунды | ТЗ п.29 допускает задержку в несколько секунд |
| Итоги завершённых | статус FINISHED | сутки | результаты неизменны после завершения (ТЗ п.28) |
| Итоги незавершённых | любой другой | **не кэшируются** | иначе кэш переживёт смену состояния |

Ключи явки и результатов **раздельные** (ТЗ п.51): кэш явки не должен
случайно стать каналом утечки результатов.

- [ ] **Step 1: Тест — результаты незавершённых выборов не кэшируются.**
- [ ] **Step 2: Тест — скрытые результаты не отдаются даже при горячем кэше.**
- [ ] **Step 3: Реализовать.**
- [ ] **Step 4: Тест — финальные результаты читаются из кэша без агрегации.**
- [ ] **Step 5: Commit**

### Task 6: Заголовки кэширования (ТЗ п.96)

**Files:** Create `apps/core/middleware.py`

| Ответ | Заголовок | Почему |
|---|---|---|
| vote status, профиль, auth, любой admin | `Cache-Control: private, no-store` | попадание в общий кэш раскрыло бы данные студента |
| публичные списки и страницы | `Cache-Control: public, max-age=...` | можно кэшировать на edge |
| всё остальное | `private, no-store` | безопасное значение по умолчанию |

ТЗ п.60 прямо запрещает CDN-кэширование vote status, профиля, admin API
и `POST /vote`. Заголовок — то, чем это обеспечивается технически.
