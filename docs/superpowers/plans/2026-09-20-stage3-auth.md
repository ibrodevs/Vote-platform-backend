# Этап 3 — Аутентификация без запроса в БД на каждый request: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Убрать `SELECT Student` из каждого authenticated-запроса, добавив при этом
проверку `is_active` и механизм мгновенного отзыва токенов — не сломав ни один
существующий токен и не сделав Redis точкой отказа.

**Architecture:** JWT проверяется криптографически локально, затем личность студента
берётся из Redis-кэша (`principal`). При промахе — один `SELECT` и запись в кэш.
В кэше лежит компактный `StudentPrincipal`, а не сериализованная Django-модель.
Полный объект `Student` подгружается лениво и только там, где реально нужен
(профиль), а горячие пути работают с принципалом. Отзыв — через `Student.auth_version`:
claim в токене сверяется с версией в принципале, расхождение = токен недействителен.

**Tech Stack:** Django 5.2.17, `django.core.cache.backends.redis.RedisCache`
(встроенный, без новых зависимостей), redis-py 8.1, PyJWT.

**Spec:** roadmap, этап 3; ТЗ п.18, 19, 20, 65, 67. Дефекты D-04, D-06 (часть auth).

---

## Global Constraints

Полный список — в roadmap. Критично здесь:

1. **Redis не источник истины и не точка отказа (ТЗ п.20).** При любой ошибке Redis
   аутентификация обязана продолжать работать через PostgreSQL. Ни один вызов кэша
   не должен уметь уронить запрос.
2. **Ни один выданный токен не ломается.** Токены живут 7 дней и лежат в `sessionStorage`
   фронтенда. Токены без claim `auth_version`, выпущенные до миграции, обязаны
   продолжать работать в течение migration period.
3. **В кэше — минимум полей (ТЗ п.18).** Никакой сериализации Django-модели:
   объект тяжёлый, тянет связи и ломается при смене схемы.
4. **Никаких PII сверх необходимого.** В принципале нет телефона, email, фото и пароля.
5. **Contract-тесты остаются зелёными**, 223 теста, 0 expected failures.
6. **Тайна голосования.** Ключи и значения кэша не связывают студента с кандидатом.

## Исходные условия (проверено 2026-09-20)

| Факт | Значение | Следствие |
|---|---|---|
| `CACHES` | не настроено вовсе | настраивается с нуля |
| Redis | доступен из контейнера (`ping: True`), redis-py 8.1 | `django-redis` не нужен, хватит встроенного бэкенда |
| Django RedisCache | `**options` уходят в пул | `socket_connect_timeout`/`socket_timeout` задаются через `OPTIONS` |
| `request.user.student` | используется в 3 местах: `voting/views.py:18,38`, `elections/views.py:384` | эти пути переводятся на принципал |
| `CombinedJWTAuthentication` | `Student.objects.select_related('university').get(...)` на каждый запрос | заменяется на Redis-first |
| `is_active` | не проверяется (D-04) | добавляется |
| Ошибка авторизации | `AuthenticationFailed(f"...{str(e)}")` (D-06) | заменяется на generic |

  - `cache_keys.NAMESPACE = "voteplatform:v1"`
  - `cache.safe_get(key, default=None)` — никогда не бросает
  - `cache.safe_set(key, value, timeout)` — возвращает `bool` успеха
  - `cache.safe_delete(key) -> bool`
  - `cache.cache_available() -> bool`

**Проектные решения:**
- Встроенный `django.core.cache.backends.redis.RedisCache` вместо `django-redis`:
  одной зависимостью меньше, а нужного функционала на этом этапе хватает.
- Таймауты **короткие** (ТЗ п.20, 95): ждать Redis секундами недопустимо, при его
  недоступности мы просто идём в PostgreSQL.
- Обёртки ловят `Exception`, а не только `redis.RedisError`: сериализация,
  пул, DNS и таймауты дают разные классы ошибок, а уронить запрос не должен ни один.

### Task 2: `auth_version` и отзыв токенов

**Files:**
- Modify: `apps/students/models.py`
- Create: `apps/students/migrations/0004_student_auth_version.py`
- Create: `apps/students/services_auth.py`
- Create: `apps/students/signals.py`
- Modify: `apps/students/apps.py`
- Test: `tests/contract/test_token_revocation.py`

**Interfaces:**
- Produces:
  - `Student.auth_version: PositiveIntegerField(default=1)`
  - `services_auth.create_student_token(student) -> str` (с claim `auth_version`)
  - `services_auth.revoke_student_tokens(student) -> int` — новая версия
  - `services_auth.invalidate_principal(student_id) -> None`

**Проектные решения:**
- Версия стартует с `1`, а не с `0`: так отличается «версия есть» от «claim отсутствует».
- Инкремент — через `F('auth_version') + 1`, а не чтением и записью: иначе два
  параллельных отзыва дадут одну версию вместо двух (та же ошибка, что в OTP-счётчике).
- Сигналы, а не явные вызовы: студентов правят и DRF-сериализатор, и Django-админка,
  и shell. Явный вызов в одном месте не закрыл бы остальные.
  **Оговорка:** `queryset.update()` сигналы не шлёт — это документируется,
  а для массовых операций даётся функция отзыва.

- [ ] **Step 1: Написать падающий тест**

```python
def test_deactivating_student_revokes_tokens(self):
    token = create_student_token(self.student)
    self.student.is_active = False
    self.student.save(update_fields=["is_active"])
    res = self.client.get("/api/v1/auth/student/me/", HTTP_AUTHORIZATION=f"Bearer {token}")
    self.assertEqual(res.status_code, 403)
```

- [ ] **Step 3: Добавить поле и миграцию.**

- [ ] **Step 4: Написать `services_auth.py` и `signals.py`, подключить в `apps.py`.**

Сигнал `pre_save`: если `is_active` сменился с True на False **или** сменился

### Task 3: `StudentPrincipal` и Redis-first аутентификация

**Files:**
- Create: `apps/core/principals.py`
- Modify: `apps/core/authentication.py`
- Test: `tests/contract/test_auth_cache.py`

**Interfaces:**
- Produces:
  - `StudentPrincipal` — `id`, `student_code`, `university_id`, `full_name`,
    `is_active`, `auth_version`; методы `to_cache()` / `from_cache()` / `from_model()`
  - `StudentUserWrapper(principal)` — `.id`, `.university_id`, `.student_code`,
    `.full_name`, `.is_student`, `.is_authenticated`, и **ленивое** `.student`

**Проектные решения:**
- В кэше лежит `dict` из шести полей, а не pickled-модель: модель тянет
  `university`, ломается при смене схемы и весит в разы больше.
- `.student` остаётся как ленивое свойство — иначе пришлось бы переписывать
  профиль и админские вьюхи, а это вне объёма этапа. Обращение к нему делает
  один `SELECT`, поэтому горячие пути обязаны его не трогать (Task 4).
- Проверки в строгом порядке: подпись → `is_active` → `auth_version`.
  Неактивный студент отсекается раньше сверки версий.
