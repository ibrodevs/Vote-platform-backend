# Этап 11 — Профилирование и вторая итерация оптимизации: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans.
> Шаги помечены `- [ ]` для отслеживания.

**Goal:** Измерить, где именно уходит время под нагрузкой, и выполнить ровно те
изменения, которые измерения оправдывают — не больше.

**Architecture:** Сначала строится измерительная оснастка (`pg_stat_statements`,
счётчик SQL round trips, профилировщик CPU воркера). Затем снимается baseline под
нагрузкой из этапа 10. Только после этого — решение об изменениях, и каждое
изменение проходит полный цикл correctness → concurrency → load → повторное измерение.

**Tech Stack:** PostgreSQL 16 `pg_stat_statements`, py-spy, k6, Django
`CaptureQueriesContext`, Prometheus histograms (уже есть с этапа 9).

**Spec:** `docs/superpowers/plans/2026-09-20-highload-roadmap.md`, этап 11;
ТЗ п. 83, 84, 117, 119, 120, 127.

## Global Constraints

Действуют все инварианты предыдущих этапов. Для этого этапа критичны:

- **Приоритет (ТЗ п.118):** КОРРЕКТНОСТЬ → ЦЕЛОСТНОСТЬ ГОЛОСА → ТАЙНА → БЕЗОПАСНОСТЬ
  → ПРОИЗВОДИТЕЛЬНОСТЬ → ЭКСПЛУАТИРУЕМОСТЬ. Оптимизация стоит **пятой**.
- **Изменение, ломающее инвариант голосования, откатывается** — без обсуждения.
- **Ничего не делаем без измерений (ТЗ п.83, 84).** Догадка «вот это наверняка
  медленно» не является основанием для изменения кода.
- **Двойной голос по-прежнему запрещает UNIQUE-ограничение базы (ТЗ п.6),**
  а не код на Python. Любая новая реализация обязана опираться на то же ограничение.
- **Один COMMIT = 1 VoteRecord + 1 Ballot (ТЗ п.5).** Успех HTTP — только после COMMIT.
- **Тайна (ТЗ п.3, 4):** профилировщик и любой новый вывод не должны печатать
  `student_id` и `candidate_id` вместе, тело `POST /vote`, заголовок `Authorization`.
- **Raw SQL — только внутри service boundary (`apps/voting/services.py`),
  никогда во views (роадмап, этап 11).** На каждый raw SQL — integration-тест.
- **Нельзя вводить sharding заранее**; нельзя переписывать на другой язык
  и дробить на микросервисы без доказательств.
- **Никаких неизмеренных заявлений о производительности (ТЗ п.85, 123).**
- Все 436 существующих тестов обязаны остаться зелёными.

## Честная рамка этапа

Железо то же, что на этапе 10: 8 ядер и 3.8 ГБ Docker на всё сразу, включая
генератор нагрузки. Из этого следует, что именно на этой машине **можно** и
**нельзя** узнать.

| Можно измерить достоверно | Нельзя |
|---|---|
| Распределение CPU между app / PostgreSQL / генератором | Абсолютный потолок RPS системы |
| Какие SQL-запросы съедают время базы (`pg_stat_statements`) | Поведение при сетевой задержке между app и БД |
| Где горит CPU внутри Python-воркера (py-spy) | Влияние диска боевого сервера на WAL |
| Число SQL round trips на одну операцию | Эффект PgBouncer под реальной нагрузкой |
| Есть ли блокировки и ожидания в базе | Работу нескольких реплик приложения |

Число round trips — метрика, **не зависящая от железа**: оно одинаково на
ноутбуке и на боевом сервере, и на сервере с сетью между app и БД каждый round
trip стоит дороже. Поэтому оно допустимо как основание для изменения кода, а
абсолютный RPS — нет.

## Задача 1: Включить `pg_stat_statements`

**Files:**
- Modify: `docker-compose.yml` (сервис `postgres`)
- Create: `apps/core/management/commands/pg_hot_statements.py`

**Produces:** команда `manage.py pg_hot_statements [--reset] [--top N]`,
печатающая таблицу: вызовы, суммарное время, среднее время, строк, текст запроса.

- [ ] **Шаг 1: добавить расширение в команду запуска PostgreSQL**

В `docker-compose.yml` к `command` сервиса `postgres` добавить
`-c shared_preload_libraries=pg_stat_statements -c pg_stat_statements.track=all`.
Расширение требует перезапуска контейнера — `docker compose up -d --force-recreate postgres`.

- [ ] **Шаг 2: создать расширение в базе**

```bash
docker compose exec -T postgres psql -U vote_user -d vote_db -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
```

- [ ] **Шаг 3: написать management-команду**

Команда читает `pg_stat_statements`, отбрасывает собственные служебные запросы,
сортирует по `total_exec_time`, печатает топ N. Запросы нормализованные —
параметры в них заменены на `$1`, поэтому персональных данных в выводе нет.

- [ ] **Шаг 4: проверить вручную**

```bash
docker compose exec -T web python manage.py pg_hot_statements --top 15
```
Ожидается непустая таблица с колонками calls / total_ms / mean_ms / rows / query.

- [ ] **Шаг 5: коммит**

```bash
git add docker-compose.yml apps/core/management/commands/pg_hot_statements.py
git commit -m "chore(perf): enable pg_stat_statements and add hot-statement report"
```
