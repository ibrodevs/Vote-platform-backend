# Этап 10 — Нагрузочное тестирование: Implementation Plan

**Goal:** Построить воспроизводимый стенд, получить **настоящие** цифры на
доступном железе и доказать, что после нагрузки данные остались целы.

**Spec:** roadmap, этап 10; ТЗ п.48, 77–82, 85–88, 90–92, 108–112, 115, 116.

---

## Честная оценка возможного

| Ресурс | Доступно |
|---|---|
| CPU | 8 ядер, общих для приложения, базы и генератора |
| RAM Docker | **3.8 ГБ** на PostgreSQL + Redis + Django + k6 |
| Сеть | loopback |

**20–40k RPS на этой машине недостижимы, и заявлять их нельзя.** Генератор
нагрузки делит те же 8 ядер с приложением — ТЗ п.109 прямо предупреждает,
что он сам становится узким местом. Поэтому:

1. Сценарии пишутся с **параметризуемым** целевым RPS, включая ступени
   до 40k — они готовы к запуску на настоящей инфраструктуре.
2. Здесь прогоняется тот масштаб, который железо выдерживает.
3. В отчёте фиксируется окружение (ТЗ п.108) и **явно указывается**,
   что цифры получены на ноутбуке и не являются подтверждением SLO из п.85.

Это прямое требование ТЗ п.123: не писать «поддерживает 40k RPS» без
результатов прогона.

## Задачи

### 1. `loadtests/` на k6 (ТЗ п.77)
- k6 запускается контейнером `grafana/k6` — локальная установка не нужна.
- Общий модуль: конфигурация из окружения, пороги, разбор ответов.
- Ни один сценарий не логирует тело `POST /vote` и токены.

### 2. Профили нагрузки (ТЗ п.79–82)
| Профиль | Что грузит | Ключевая проверка |
|---|---|---|
| A | публичные чтения | масштабируется ли кэшируемое чтение |
| B | аутентифицированные чтения | убирает ли Redis запрос к базе на каждый запрос |
| C | смешанный реалистичный | 55/15/15/10/5 по ТЗ п.81 |
| D | запись голосов | **отдельно**: 40k HTTP ≠ 40k durable writes |

### 3. Генератор данных и токенов (ТЗ п.78)
- Уже есть `generate_test_data`. Дополняется выгрузкой JWT для k6:
  без готовых токенов профиль B и D невозможны.

### 4. Валидация целостности после прогона (ТЗ п.87, 115)
- `verify_election_integrity` — отдельная команда.
- **Нагрузка без проверки целостности не считается валидным прогоном.**
  Проверяется: число VoteRecord и Ballot, отсутствие дублей, orphan-бюллетеней
  и частичных голосов.

### 5. Soak, spike, recovery (ТЗ п.110–112)
- Сценарии описаны и запускаемы; на этом железе прогоняются сокращённо.

### 6. Отчёт (ТЗ п.90, 91, 108)
- `docs/LOAD_TESTING.md`: как запускать.
- `docs/PERFORMANCE.md` раздел 5: окружение, цифры, оставшееся узкое место,
  оценка трафика.

## Definition of Done

- [ ] `loadtests/` в репозитории, запускается одной командой.
- [ ] Четыре профиля + soak/spike/recovery.
- [ ] Целевой RPS параметризуем, ступени до 40k описаны.
- [ ] `verify_election_integrity` работает и вызывается после каждого прогона.
- [ ] Получены **реальные** цифры с зафиксированным окружением.
- [ ] Проверено, не был ли генератор узким местом (ТЗ п.109).
- [ ] После нагрузки: VoteRecord == Ballot, ноль дублей, ноль orphan.
- [ ] В документации прямо сказано, чего эти цифры **не** доказывают.
