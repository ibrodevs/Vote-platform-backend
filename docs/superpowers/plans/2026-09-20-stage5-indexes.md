# Этап 5 — Индексы и schema performance: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development
> или superpowers:executing-plans. Шаги отмечаются чекбоксами.

**Goal:** Привести планы горячих запросов в порядок, добавив индексы **только там,
где `EXPLAIN` доказал необходимость**, и закрыть гонку при регистрации по email
констрейнтом уровня базы.

**Architecture:** Работа измерительная, а не умозрительная. Сначала генерируется
объём данных, на котором планировщик PostgreSQL ведёт себя как в production
(на 19 строках он всегда выбирает Seq Scan, и любой вывод был бы ложным).
Затем `EXPLAIN (ANALYZE, BUFFERS)` по каждому горячему запросу — до и после.
Индекс, не изменивший план, не добавляется: каждый лишний индекс замедляет
запись и занимает место.

**Tech Stack:** PostgreSQL 16, Django 5.2, `pg_trgm` (только если EXPLAIN потребует).

**Spec:** roadmap, этап 5; ТЗ п.14, 15, 54, 94.

---

## Global Constraints

Полный список — в roadmap. Критично здесь:

1. **Ни одного индекса без EXPLAIN.** ТЗ п.14 прямо это требует. Индекс —
   не бесплатное улучшение: он замедляет каждый INSERT и UPDATE таблицы.
2. **Ни одного дублирующего индекса.** UNIQUE-констрейнт уже создаёт B-tree;
   отдельный Index по тем же колонкам — чистая потеря.
3. **Миграция не удаляет данные.** При найденных дубликатах email миграция
   обязана остановиться с понятной инструкцией, а не «починить» данные (ТЗ п.15).
4. **Для больших таблиц — `CREATE INDEX CONCURRENTLY`** (ТЗ п.54): обычный
   `CREATE INDEX` держит блокировку записи на всю таблицу.
5. **Contract-тесты не меняются.** Индексы не имеют права поменять ответы.

## Почему нужен генератор данных

`EXPLAIN` на таблице в 19 строк всегда покажет `Seq Scan` — планировщику
дешевле прочитать страницу целиком, чем идти в индекс. Любой вывод об
индексах, сделанный на таких данных, будет неверным.

ТЗ относит генератор к этапу 10 (п.78), но без него этап 5 невозможно
выполнить честно. Поэтому базовая версия команды делается здесь,
а на этапе 10 расширяется до 1M студентов и JWT-данных для нагрузки.

**Целевой объём для анализа планов:**
| Таблица | Строк |
|---|---|
| Университеты | 20 |
| Студенты | 200 000 |
| Выборы | 60 |
| Кандидаты | 600 |
| VoteRecord | 120 000 |
| Ballot | 120 000 |

### Task 3: Аудит планов и добавление индексов

**Files:** модели + миграции

Порядок работы по каждому запросу:
1. посмотреть план;
2. если `Seq Scan` по большой таблице или высокая стоимость — понять, какого
   индекса не хватает;
3. добавить индекс;
4. перепроверить план;
5. **если план не изменился — индекс откатить.**

Кандидаты на проверку (из ТЗ п.14), но решение — по EXPLAIN:

| Таблица | Паттерн |
|---|---|
| `Ballot` | `WHERE election_id`, `GROUP BY candidate_id` |
| `VoteRecord` | `WHERE election_id` (явка), `WHERE student_id` (доступные выборы) |
| `Election` | `university_id + status + окно времени` |
| `Candidate` | `election_id + order` |
| `Student` | `university_id + student_id`, `email`, `is_active` |

- [ ] **Step 1–5:** по циклу выше для каждого запроса.
- [ ] **Step 6: Проверить, что не осталось дублирующих индексов.**
- [ ] **Step 7: Commit**

### Task 4: Case-insensitive UNIQUE на email (ТЗ п.15)

**Files:** `apps/students/models.py`, миграция, тесты

Сейчас регистрация проверяет `Student.objects.filter(email__iexact=...).exists()`
перед INSERT. Два параллельных запроса пройдут проверку одновременно —
классическая гонка, та же по природе, что была в голосовании.

**Решение:** `UniqueConstraint(Lower('email'), condition=Q(email__isnull=False) & ~Q(email=''), name=...)`.
Частичный индекс: пустые и NULL email дубликатами не считаются, их в базе много.

**Миграция обязана остановиться при существующих дубликатах** и напечатать,
что делать. `audit_db_data` уже умеет их искать — миграция вызывает ту же проверку.

- [ ] **Step 1: Тест — параллельная регистрация одного email даёт одного студента.**
- [ ] **Step 2: Прогнать — падает.**
- [ ] **Step 3: Констрейнт + миграция с guard'ом.**
- [ ] **Step 4: Тест самого guard'а: при дубликатах миграция падает с инструкцией.**
- [ ] **Step 5: Обработать `IntegrityError` в регистрации** — отдавать тот же
      `email_already_exists`, а не 500.

### Task 5: Поиск по студентам (ТЗ п.94)

Админский поиск использует `icontains` по пяти полям. На миллионе строк это
пять `ILIKE '%...%'`, ни один B-tree индекс тут не работает.

Решение принимается **по EXPLAIN**: либо `pg_trgm` + GIN, либо ограничение
минимальной длины запроса, либо и то и другое. Расширение `pg_trgm` требует
прав суперпользователя — если их нет, это фиксируется как требование к деплою.

- [ ] **Step 2: Решение по результату, реализация.**
