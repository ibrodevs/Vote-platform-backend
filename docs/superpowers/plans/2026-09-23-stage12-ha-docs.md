# Этап 12 — Read replica, backup, HA, документация и финальный отчёт: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans.

**Goal:** Довести систему до состояния, в котором её можно эксплуатировать:
готовность к реплике чтения, проверенная процедура восстановления из бэкапа,
описанная топология отказоустойчивости, типизация критичной логики и финальный
отчёт по 28 пунктам Definition of Done.

**Architecture:** Реплика вводится как **явная подписка**, а не как
автоматический роутинг: по умолчанию всё читает primary, и только запросы,
для которых устаревание данных заведомо безопасно, помечаются вручную.
Бэкап не считается сделанным, пока из него не восстановились.

**Spec:** roadmap, этап 12; ТЗ п. 46, 47, 90, 99, 100, 104, 105, 116, 123–126.

---

## Global Constraints

- **Приоритет (ТЗ п.118)** прежний: корректность → целостность голоса → тайна →
  безопасность → производительность → эксплуатируемость.
- **Свежий статус голоса нельзя читать с отстающей реплики (ТЗ п.46).**
  Это не рекомендация: студент, увидевший «вы ещё не голосовали» после
  успешного голоса, нажмёт кнопку второй раз.
- **`POST /vote`, статус голосования сразу после голоса, admin start/finish —
  только primary.**
- **Никаких sticky sessions (ТЗ п.99).** Падение одной ноды не должно
  затрагивать пользователей, обслуживаемых остальными.
- **Никаких заявлений о производительности без ссылки на benchmark (ТЗ п.123).**
- Все 443 существующих теста обязаны остаться зелёными.
- API-контракт не меняется.

## Задача 1: Готовность к реплике чтения (ТЗ п.46)

**Ключевое решение:** роутер Django выбирает базу **по модели**, а нужный здесь
критерий — не модель, а смысл запроса. Одна и та же модель `VoteRecord` читается
и в проверке «голосовал ли я» (критично), и в отчёте (не критично).
Поэтому автоматического роутинга чтений не будет: по умолчанию всё идёт
на primary, реплика — только там, где это написано явно.

Это направление ошибки выбрано намеренно: забытая пометка даёт лишнюю нагрузку
на primary, забытый запрет — показывает студенту устаревший статус голоса.

- [ ] **Шаг 1: тест, что запись никогда не уходит на реплику**
- [ ] **Шаг 2: `apps/core/db_replica.py` и `config/db_router.py`**
- [ ] **Шаг 3: alias `replica` в settings, включается переменной окружения**
- [ ] **Шаг 4: пометить заведомо безопасные чтения** (новости, FAQ,
      статические страницы, список вузов) — там устаревание на секунды
      безвредно и никак не связано с голосованием.
- [ ] **Шаг 5: тест, что статус голосования и голосование читают primary**
- [ ] **Шаг 6: без переменной окружения поведение не меняется вовсе**
- [ ] **Шаг 7: коммит**

## Задача 2: Бэкап с проверенным восстановлением (ТЗ п.47)

**«Делать бэкапы» — не требование.** Требование — уметь восстановиться.
Поэтому скрипт восстановления пишется и **проверяется прямо здесь**, на
работающей базе в Docker, а не описывается словами.

- [ ] **Шаг 1: `scripts/backup.sh`** — `pg_dump -Fc`, отказ при пустом дампе.
- [ ] **Шаг 2: `scripts/restore.sh`** — восстановление с обязательным
      подтверждением: команда, стирающая базу, не должна запускаться случайно.
- [ ] **Шаг 3: `scripts/verify_backup.sh`** — восстановление во временную базу
      и сверка числа строк по ключевым таблицам, включая `VoteRecord`/`Ballot`.
- [ ] **Шаг 4: прогнать все три на реальных данных и записать вывод**
- [ ] **Шаг 5: раздел о WAL archiving / PITR в документации**
- [ ] **Шаг 6: коммит**
